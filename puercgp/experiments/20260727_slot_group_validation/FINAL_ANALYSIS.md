# 固定槽位分组与 SM 隔离验证报告

日期：2026-07-27  
代码版本：`a2281fb` 加本实验目录中的未提交实验代码  
结论对象：BFS、固定槽位组、组级整批补充、普通 CUDA Stream、Green Context SM 隔离

## 1. 结论先行

固定槽位组是一个**有条件有效、但不能默认启用**的机制。

1. 逐槽补充没有体现预期收益。它虽然能让新查询更早进入系统，但会混合不同 BFS 阶段，并破坏拉取阶段连续、规整的查询槽位访问。相对 64 槽整批补充，它在全推送下慢 3.4% 至 25.6%，在拉取或混合模式下最差慢 58.4%。
2. 固定 `2x32` 分组解决了逐槽补充的规整性问题，但两个普通 Stream 会直接竞争共享的 HBM/L2。四张社交或引用图的全推送性能均下降，吞吐仅为整批 64 槽的 0.64x 至 0.76x。
3. Green Context 的 `40+40` SM 隔离不能隔离 HBM/L2，因此也不是通用解。它在四张常规图的全推送下仍只有 0.78x 至 0.82x。
4. 两类例外工作负载存在稳定收益：
   - roadNet-CA 全推送：`2x32 @ 40+40 SM` 在 N=256/400/800 时分别提升 1.08x、1.14x、1.15x，同时改善 P50/P95/P99 延迟。
   - soc-twitter 拉取与混合：正式复测分别提升 1.45x 和 1.31x；普通双 Stream 也分别提升 1.32x 和 1.24x，说明收益来自真实并行，而不只是 Q=32 算子本身更快。
5. Nsight Compute 表明，Twitter 代表性拉取算子仅达到 31.0% 的显存峰值吞吐和 19.1% 的 SM 峰值吞吐，明显低于其余图的 52.6% 至 62.0% 显存吞吐。固定分组在这里能用第二组工作填补访存延迟造成的空闲资源。
6. 当前最合理的系统设计不是动态地逐轮重分 SM，而是：默认使用 Q=64 整批执行；预先创建固定 `40+40` Green Context；仅在识别出长直径小前沿，或低带宽利用率的高延迟拉取阶段时，于**组边界**启用 `2x32` 并发。

## 2. 被验证的设计

### 2.1 调度粒度

全局查询队列先按 32 个查询切成 cohort，再轮转分配给两个固定组：

```text
全局队列: C0 C1 C2 C3 C4 C5 ...
组 0:     C0    C2    C4    ...
组 1:        C1    C3    C5 ...
```

每个组内部最多保留 32 个活跃槽位。只有当本组 32 个槽位全部可复用时，才注入下一整个 cohort；最后不足 32 个查询的尾批次执行紧凑化处理。这样不会在一轮中混合旧查询和刚进入的查询，也不会产生稀疏的活跃槽位布局。

### 2.2 组间执行方式

实验实现了三种组间方式：

| 方法 | 含义 | 目的 |
|---|---|---|
| `group_serial` | 两个 Q=32 组在全 GPU 上顺序执行 | 分离 Q=64 拆分损失与并发收益 |
| `group_stream` | 两个独立普通 Stream 并发执行 | 验证原生 CUDA 并发是否足够 |
| `group_green` | 两个组在 `40+40 SM` Green Context 上并发 | 限制 SM 干扰并保留并发 |

另外测试了 `4x16 @ 20 SM`，用于判断更细分组能否进一步隐藏长直径图中的每步固定开销。

### 2.3 对照方法

| 方法 | 说明 |
|---|---|
| `static64` | 每 64 个查询构成一个静态批次，完成后处理下一批 |
| `cohort64` | 复用 replenish 引擎，但只在 64 个槽位整批完成后补充 |
| `immediate64` | 每出现一个可复用槽位就立即注入一个查询 |

`cohort64` 与 `static64` 的计算粒度相同，但前者复用执行缓冲区，因此本文主要以 `cohort64` 作为大批次基线，同时保留 `static64` 数据防止缓冲区复用带来误判。

## 5. 正确性验证

构造了一个非均匀度数的 8 顶点图，并使用固定源节点验证：

- 推送、拉取、混合三种模式；
- `cohort64`、普通双 Stream、`40+40 SM` Green Context；
- `4x16` Green Context；
- N 不能被组大小整除的尾批次。

每个查询输出 `(可达顶点数, BFS 层级和)` 指纹。所有固定组结果均与整批参考结果逐查询一致。E1 的四张真实图还验证了 N=64 下 `4x16` 与 Q=64 的逐查询指纹一致。

因此，当前结论不依赖 `discard_results` 路径下无法观察输出的假设；性能实验和正确性实验分别运行。

## 6. 补充粒度实验 E0

roadNet-CA 使用高、低偏心率源节点交错形成的 N=400/800 长尾队列，Q=32，全推送。加速比均相对静态 Q=32 批次。

| N | chunk=1 | chunk=4 | chunk=8 | chunk=16 | chunk=32 |
|---:|---:|---:|---:|---:|---:|
| 400 | 0.926x | 0.927x | 0.947x | 0.951x | 0.981x |
| 800 | 0.889x | 0.902x | 0.931x | 0.939x | 0.976x |

粒度越大，性能单调改善，没有中间最优点。逐槽补充虽然把 N=800 的全局计算步数从 19847 降低到 17255，但每步耗时增加 29.4%，最终仍慢 11.1%。chunk=32 的步数与静态批次几乎相同，每步开销也只高 2.4%。

这说明 replenish 的主要问题不是 reset 算子本身，而是不同阶段查询进入同一 shared frontier 后，提高了每个全局 step 的物理工作量，并破坏了访问规整性。

## 8. N=256 全推送实验 E2

### 8.1 常规图

括号内为相对 `cohort64` 的吞吐加速比。

| 数据集 | `static64` | `cohort64` | `immediate64` | 普通 `2x32` | Green `2x32` |
|---|---:|---:|---:|---:|---:|
| cit-Patents | 1462.7 (0.96x) | 1405.7 (1.00x) | 1754.5 (0.80x) | 2211.9 (0.64x) | 1750.6 (0.80x) |
| soc-orkut | 2202.7 (1.00x) | 2194.9 (1.00x) | 2269.1 (0.97x) | 3043.7 (0.72x) | 2825.4 (0.78x) |
| soc-twitter | 7130.7 (0.99x) | 7056.4 (1.00x) | 8864.8 (0.80x) | 9255.8 (0.76x) | 8597.2 (0.82x) |
| soc-sinaweibo | 8783.0 (0.84x) | 7400.6 (1.00x) | 8853.4 (0.84x) | 11098.4 (0.67x) | 9469.3 (0.78x) |

固定分组在常规全推送图上没有形成收益。原因包括：

1. Q=64 能在 shared frontier 中合并更多查询的邻接访问；拆成两个 Q=32 后，这部分跨组共享永久丢失。
2. 普通双 Stream 不能限制并发强度，HBM/L2 干扰最明显。
3. Green Context 只改善普通 Stream 的 SM 干扰，无法恢复跨组共享，也无法隔离显存系统。
4. `immediate64` 同样没有降低延迟。其 P50 与 P95 通常也高于 `cohort64`，说明更早注入查询没有抵消阶段混合成本。

|---:|---:|---:|---:|---:|---:|

N 增大后，`2x32` Green 的收益从 1.08x 增至 1.15x。普通 Stream 始终更慢，说明收益依赖 SM 隔离带来的稳定并发，而不是仅仅开两个队列。

## 10. 硬件归因

选择真实 BFS 状态中的高工作量拉取迭代，Q=32、80 SM，只剖析 `fused_pull_simple_kernel`：

| 数据集/迭代 | kernel | 有效 DRAM 带宽 | DRAM 峰值 | SM 峰值 | 长记分板停顿 |
|---|---:|---:|---:|---:|---:|
| cit / 8 | 9.81 ms | 531.8 GB/s | 59.23% | 33.32% | 59.81% |
| orkut / 4 | 36.21 ms | 557.3 GB/s | 62.04% | 25.79% | 46.53% |
| twitter / 6 | 156.98 ms | 278.4 GB/s | **31.02%** | **19.10%** | 51.74% |
| sinaweibo / 4 | 139.91 ms | 472.9 GB/s | 52.64% | 36.41% | 43.11% |

推断如下：

1. Twitter 的邻居值读取更不规则，单个 Q=32 拉取组同时表现出低显存吞吐、低 SM 吞吐和较高的长记分板停顿，属于访存延迟受限但尚未把 HBM 吞吐压满的状态。
2. 两个并发组提供更多独立访存请求，提高设备级 memory-level parallelism。普通 Stream 已有 1.32x 收益，Green Context 再通过固定 SM 归属降低调度干扰，达到 1.45x。
3. cit 和 orkut 单组已经达到约 60% 显存峰值；加入第二组时，每组耗时接近翻倍，重叠不能转化为净收益。
4. sinaweibo 的 SM 与显存吞吐也高于 Twitter，且全图规模使两个完整拉取状态的竞争更重，因此分组变慢。

这些指标来自单个代表性迭代，能够支持机制解释，但还不能直接作为跨数据集在线分类器。

## 11. 关于动态 SM 划分

本实验没有在每轮动态改变 SM 数量，而是在执行前一次性创建 `40+40` 或 `20x4` 分区。原因是：

1. 已运行的 Green Context 不能在 kernel 执行中透明扩缩 SM。
2. 重新划分需要等待相关 Stream 上的 kernel 排空，然后销毁或切换 context/stream。这个过程天然需要同步点。
3. 如果每个 BFS iteration 都重分区，同步、上下文管理和策略抖动很可能超过短 kernel 的收益。

如果后续需要动态选择，建议使用“固定资源池 + 组边界切换”：

- 程序启动时预建全 GPU 路径和 `40+40` 两组路径；
- 一个 cohort 完成后形成天然同步点；
- 只在该边界决定下一组走 Q=64 还是 `2x32`；
- 不修改正在执行的 Green Context，也不在单个 iteration 内重分 SM。

该做法保留了动态策略的选择能力，但把物理资源划分固定下来。

## 12. 最终设计建议

### 12.1 默认路径

- 默认 Q=64、`cohort64` 或现有静态大批次。
- 不启用逐槽补充。
- 不默认开启多 Stream 或 Green Context 分组。

### 12.2 可选的固定分组路径

只保留 `2x32 @ 40+40 SM`，在以下场景候选启用：

1. 长直径、连续多轮 shared frontier 很小的全推送查询，例如 roadNet-CA。
2. 拉取阶段单组显存吞吐和 SM 吞吐均低、同时存在明显长记分板停顿的高度不规则图，例如 soc-twitter。

不建议保留 `4x16` 作为常规配置。它没有随 N 增大继续提升，而且进一步损失查询共享和 query-lane 宽度。

### 12.3 启用判据

下一步可先构造保守的离线或低频在线判据，而不是复杂 predictor：

- 推送：最近若干轮的 shared-frontier 顶点数、union edge 数、每轮 kernel 时间和图直径代理；
- 拉取：首个代表性拉取轮的 kernel 时间、估算访存字节数，以及由时间反推的有效带宽；
- 只有预测的两组 makespan 小于 Q=64 时间至少 10% 时才切换，给误差和切换成本留余量；
- 一旦进入固定分组模式，至少执行完整 cohort，避免逐轮来回切换。

## 13. 对当前方案的客观判断

固定组方案成功验证了两个重要事实：

1. 你的担忧成立，逐槽级灵活性确实会破坏拉取规整性并提高全局 step 成本。
2. 更粗的组级调度能够在特定延迟受限工作负载上同时改善吞吐和尾延迟。

但实验也否定了“把大 batch 普遍拆成多个独立组即可获益”的假设。跨组丢失 sharing 和共享显存干扰在多数图上更强。当前结果适合作为一个**有明确适用条件的资源调度优化**，不适合作为替代现有大批次执行的统一机制。

如果论文需要把它作为核心贡献，还需要在更多图和至少另一代 GPU 上证明可预测的工作负载类别，并实现低成本启用判据。否则，更稳妥的定位是系统中的特例优化及负面设计经验。

## 14. 局限与后续验证

- 当前只验证 BFS，没有验证 SSSP、SSWP、PR/PPR。
- 只验证一台 V100；Green Context 和显存行为可能随 GPU 架构变化。
- 四图拉取/混合筛选为 3 次重复，只有 Twitter 做了 5 次正式复测。
- NCU 只剖析一个代表性迭代，没有记录端到端所有迭代的硬件指标。
- 当前固定组按输入顺序轮转，没有结合 selective batching 或 offset 排序。
- 未实现组内部分查询 push、部分查询 pull，也没有验证 push/pull 两类组同时运行。

推荐后续顺序：

1. 先增加 2 至 4 张长直径图和 2 至 4 张高度不规则大图，验证两类收益能否复现。
2. 在 A100/H100 上复测 `cohort64` 与 Green `2x32`，确认结论是否依赖 V100。
3. 只为候选工作负载实现 cohort 边界的启用判据。
4. 判据稳定后，再考虑与 selective batching、offset 或 query-level push/pull 划分组合。
